# wink 扩展规划：连续多文件 + 多类型剪贴板粘贴

**日期**：2026-08-19
**分支**：main（v0.1.0 基线，干净）
**涉及组件**：sender-web（TS）、receiver（TS）、shared（TS）、sender-cli（Rust，需求 1 可选）
**协议影响**：需求 1 协议零改动；需求 2 可能零改动（复用既有容器类型）

---

## 背景 / 现状

- 发送端（web + cli）**单文件**：web 的 `file-input` 无 `multiple`，change 只读 `files[0]`；cli 只认 `args[1]`，多余裸参数被忽略
- 粘贴仅**文本**：web `paste-btn` 用 `prompt()` 弹框收文本 → 打成 `WNKT` 文本容器
- 接收端**一次一个 session**：TP 端 `onComplete` 后 `decoding=false`，自动隐藏镜头（enterHiddenMode），需用户手动点"▶ 继续接收"才开始下一个 → 无法自动衔接连续流
- 协议容器三种：`WNK1`(文件) / `WNKT`(文本) / `WNKM`(manifest)
- manifest `payloadType: 0=file 1=text`
- **接收端已有按 sessionId 重置的能力**（`identity !== currentIdentity` 时重建解码器，receiver/src/main.ts L137-142）

## 需求 1：连续多文件

### 目标
发送端选/队列多个文件后，自动按序一个接一个传；接收端收到全部。

### 核心难点（单向信道的本质）
单向光学信道无反馈、无握手。难点不在"发送端播下一个"，而在**接收端如何无歧义地知道"上一个传完、该等下个新流"**。

关键洞察：**接收端其实已经有跨 session 自动重置逻辑**（`identity` 变化 → 重建解码器）。理想情况下，接收端在一个 session complete 后，**只要继续监听下一个 manifest/流，就能自动衔接**。所以连续传输的接收端侧是"完成一个 → 不冻结，继续等下一个流"，配合发送端自动切换到下一个文件。

### 方案 A：发送端自动队列（推荐）
- **发送端**：支持选择多个文件（web `multiple` + 拖拽多文件；cli 接受多个裸路径），维护文件队列
- **发送端交互**：当前文件传完后，**自动切换到下一个文件**（重打包 → 新 manifest → 新 sessionId → 播帧流），期间显示"正在传 2/5：xxx"
- **接收端**：`onComplete` 后**不进入冻结停止**，而是恢复到"等待下一 manifest"状态（保留镜头、清空上一次状态、继续解码循环）—— 用已有的 `identity` 变化自动重置
- 全部传完后，发送端停下（队列空），接收端 `onComplete` 显示最后一个文件 + 常规隐藏
- **新增交互**：发送端队列面板（列表 + 移除 + 顺序）；接收端"共 N 个文件 · 已收 M"计数

### 方案 B：接收端结束冻结 + 手动触发下一个（轻量）
- 保持"传完一个自动隐藏 + 手动继续"的现有交互，但发送端支持预选多个，用户每次点"继续接收"前发送端已就绪下一个
- 缺点：不真正"连续"，需要用户手动干预，违背用户"连续"的诉求

**（选 A，用户已明确要"连续"）**

### 技术要点
1. **web 多选**：`<input type="file" multiple>` + `dataTransfer`（拖拽）支持
2. **cli 多参**：`wink a.jpg b.png` → 收集 `args` 中所有非 `--` 前缀的裸路径为队列（现在 `parse_arg` 用带前缀参数，裸路径可全部收集）
3. **队列状态机**（web + cli 一致）：空闲 → 播当前文件 → complete/超时 → 队列非空则切下一个 → 空则停止
4. **接收端无协议改动**：靠 sessionId 天然隔离。但需处理"两个 session 边界"——前一个 complete 后、后一个 frame 到来前，`decoder` 需被下一个 manifest/流的 identity 重置（已有逻辑）
5. **接收端 UI**：文件计数 + 队列序号；避免每次 complete 都走 enterHiddenMode（连续模式不隐藏，最后才隐藏）

### 风险
- **丢帧导致"卡在等待"**：单向信道发送端永远不知道接收端是否收到某个文件。若某文件丢帧过重，接收端永远等不齐该文件 → 无法自动切下一个。**需要超时/手动跳过兜底**：接收端"卡住 N 秒"提示，或发送端每文件播固定冗余后自动切（但可能丢尾巴）
- **这是连续传输最大的工程难点**，规划时必须明确兜底策略

### 兜底策略（待用户选）
- A1：每文件发送端播满 `1.15K × 安全系数` 帧后无论接收端是否收到都强制切下一个（简单，但可能丢文件）
- A2：接收端检测"某 session 长时间未完成且无新帧"→ 提示"是否跳过/重传"（可靠，但要人工）
- **建议 A2**（符合 wink 手动纠偏的既有哲学 + 用户"触发点纪律"）

## 需求 2：粘贴多类型内容

### 目标
粘贴（clipboard）不只文本，还支持图片、HTML、文件等，按类型走对应容器。

### 现状
`paste-btn` → `prompt()` 只捕获文本 → `packSnippet` 打包 `WNKT`。**只有文本一种剪贴板类型。**

### 浏览器剪贴板现实约束（关键）
- `prompt()` **永远拿不到非文本**——只能靠 `navigator.clipboard.read()`（异步读多种类型）
- `navigator.clipboard.read()` 需要：**① 用户手势（点击按钮/粘贴事件）② 权限（clipboard-read）③ 部分浏览器（Chrome 桌面）才完整支持多类型**；`readText()` 只读文本
- 更可靠：监听全局 `paste` 事件（`document.addEventListener('paste', e => e.clipboardData.items)`)——这是标准做法，能拿到 `image/png`、`text/html`、`text/plain`、`files` 等多种 Item

### 方案（推荐：全局 paste 事件 + 类型路由）
1. **交互**：页面任意位置 `paste`（Ctrl+V / 右键粘贴）→ 读取 `clipboardData.items`；同时保留一键按钮聚焦
2. **类型路由**（按 `item.type` 优先级）：
   - `image/*` → 打包成**图片容器**（新）
   - `text/html` → 存 HTML + 纯文本双份（新容器 / 文本容器带 html 标记）
   - `text/plain` → 现有 `WNKT` 文本容器
   - `files`（`item.kind === 'file'`）→ 现有 `WNK1` 文件容器
3. **新容器类型**：图片（`WNKI`？）和富文本（`WNK2`？）——**需新增容器 magic**，或复用文本容器扩展
4. **接收端**：按容器 magic 分发呈现（图片预览、HTML iframe、文本全文）

### 协议影响（待定）
- 若新增图片/富文本容器 → **新 magic 常量 + manifest payloadType 扩展**（0=file 1=text 2=image 3=richtext）→ **协议不兼容改动 → version bump**
- 若只做"粘贴到文件"（把图片当文件走 WNK1）→ **协议零改动**，只是发送端交互增强

**关键决策点：粘贴图片/富文本是"当文件传（接收端下载）"还是"当富文本内嵌呈现（接收端渲染）"？**
- 前者：零协议改动，逻辑复用，但接收端呈现=普通文件下载
- 后者：需要新容器 + payloadType 扩展 + 接收端渲染逻辑，协议改动大
- **建议先做前者（图片当文件传），富文本内嵌呈现作为后续**，符合渐进落地

## 实施顺序（提案）

**阶段 1：连续多文件（需求 1）**
1. sender-web：input multiple + 多文件拖拽 + 队列状态机
2. sender-web：自动切下一个 + 队列 UI（序号/总数/当前）
3. receiver：完成不冻结、连续等待下一个 session（复用 identity 重置）+ 文件计数
4. receiver：卡住兜底提示（A2）
5. sender-cli：多裸路径参数 → 队列（若决策 2 选 cli）
6. 端到端验证（两个文件连传）

**阶段 2：多类型粘贴（需求 2）**
1. sender-web：全局 paste 事件 + clipboardData 读取
2. 类型路由（image→文件容器 / text→WNKT / file→WNK1）
3. receiver：按类型呈现（图片预览等）
4. 协议是否扩展（视决策 3）
